# 「桌游馆」(DesktopGames) 设计文档

- 版本：v0.1（设计稿，待评审）
- 日期：2026-10-15
- 范围：整体架构、前后端设计、游戏插件框架、美术/音频方案、测试与部署

---

## 1. 产品定位

一个面向**朋友局**的线上桌游平台：一人开房、发链接邀请，大家浏览器点开即玩，无需安装、无需注册、无语音通话（用游戏内文字聊天 + 表情回应代替）。

**目标用户**：本人 + 朋友，单房间 2–11 人，总并发房间数量级在几十以内（熟人邀请制，不做匹配）。

**核心诉求（按优先级）**：

1. 玩法正确、稳定不掉线（社交推理游戏的裁判必须可信）
2. 美术与动画有质感（卡牌 3D 翻转、粒子氛围、结算演出）
3. 音乐与音效贴合场景（大厅/轮抽/夜晚/结算各阶段）
4. 新游戏接入成本低（插件化游戏框架）

**明确的非目标（MVP 不做）**：

- 语音/视频通话
- 公网大规模并发、匹配系统、排位
- 付费、账号体系（身份 = 浏览器本地档案：昵称 + 头像）
- 移动 App（但 Web 必须适配手机浏览器）

## 2. 总体架构

```
┌────────────────────────┐         WSS (Socket.IO)          ┌──────────────────────────┐
│  Web 客户端 (React+TS)  │ ◄──────────────────────────────► │  权威游戏服务器 (Node+TS)  │
│  ┌──────────────────┐  │      action(带seq) ──►           │  ┌────────────────────┐  │
│  │ 表现层            │  │      ◄── event(动画/音效 cue)     │  │ 房间管理器           │  │
│  │  React UI / 卡牌   │  │      ◄── view(按座位过滤的状态)   │  │ 游戏插件(纯逻辑)      │  │
│  │  粒子层 / 音频     │  │                                  │  │ 会话/重连/时钟        │  │
│  └──────────────────┘  │                                  │  └────────────────────┘  │
└────────────────────────┘                                  │  SQLite(战绩, M5 可选)    │
                                                            └──────────────────────────┘
```

**三条铁律**：

1. **服务端权威**：所有规则判定在服务器完成；隐藏信息（身份、手牌）永不以明文下发，客户端每次只收到「以我的座位视角计算的视图」。
2. **逻辑与表现分离**：游戏逻辑是纯函数 reducer，产出**事件流**（`card:played`、`assassinate`、`reveal`…）；客户端根据事件播动画、放音效，再按视图渲染状态。同一份裁判可以被人类客户端、机器人、回放器共用。
3. **灰盒先行**：先用占位美术把玩法跑通并测试，再灌入主题美术。避免「美术返工拖死玩法验证」。

## 3. 技术选型

| 层 | 选择 | 理由 | 备选与否决原因 |
|---|---|---|---|
| 前端框架 | React 18 + Vite + TypeScript | 生态成熟、动画库齐全 | Vue 亦可，团队熟悉度决定 |
| 客户端状态 | zustand | 轻量、无样板代码 | Redux 过重 |
| UI 动画 | Framer Motion | 布局动画/手势/编排方便 | — |
| 卡牌动画 | CSS 3D transform（`preserve-3d`） | 翻牌/发牌天然适合，无需游戏引擎 | PixiJS：粒子效果简单，不值得引入，改为自写 ~200 行 canvas 粒子层 |
| 氛围粒子 | 自写 canvas 粒子层（萤火/落樱/尘埃） | 依赖少、可控性能 | — |
| 高光演出 | Lottie（结算、胜利动画） | 设计师友好的矢量动画 | — |
| 音频 | Howler.js | 跨浏览器音频、音量组、淡入淡出 | 原生 WebAudio 直接写要处理太多兼容 |
| 通信 | Socket.IO | 房间语义、断线重连、心跳内置 | Colyseus：自带状态同步很诱人，但按座位过滤隐藏信息的自定义灵活性不足，且调试链路更黑盒；用 Socket.IO + 自定义视图协议更可控 |
| 协议校验 | zod（前后端共享 schema） | 一份类型两处使用 | — |
| 服务端 | Node.js 20 + TypeScript | 与前端同语言，共享 `packages/protocol` | — |
| 持久化 | 内存（房间/对局）+ SQLite（战绩，M5） | 小规模无需 Redis/PG；服务器重启丢房间可接受（文档化） | — |
| 测试 | vitest（单元/集成）+ Playwright（多标签 E2E）+ 机器人客户端（soak） | 多人游戏 E2E 用多 browser context 模拟 | — |
| 部署 | Docker Compose + Caddy（自动 TLS） | 单机一键部署 | — |

## 4. 前端设计

### 4.1 页面与路由

| 路由 | 内容 |
|---|---|
| `/` | 大厅：昵称/头像设置、创建房间、输入邀请码加入、游戏橱窗（卡片式展示已集成游戏） |
| `/room/:code` | 等待室 → 对局（同一页面内状态切换）：玩家列表、聊天、游戏桌面 |
| `/help/:gameId` | 内嵌规则页（图文/交互动画演示） |
| `/settings` | 音量、动画强度（低配模式）、`prefers-reduced-motion` 跟随 |

### 4.2 渲染分层

- **L1 React DOM**：HUD、玩家列表、聊天、**卡牌**。卡牌用 CSS 3D 实现翻面/堆叠/飞行，`framer-motion` 编排入场与布局过渡。
- **L2 Canvas 粒子层**：全屏、`pointer-events: none`、requestAnimationFrame 单循环，绘制环境粒子（萤火虫、落樱、尘埃）与瞬时爆发（刺杀火花）。数量随「低配模式」与设备分级缩放。
- **L3 Lottie 演出层**：回合结算、最终胜利等低频高光时刻的全屏演出。

**动画原则**：一切卡牌/游戏动画由服务器**事件驱动**（同一事件在所有客户端播放同一动画，按事件序号 stagger 错峰）；所有动画可被 `prefers-reduced-motion` 与低配模式降级为淡入淡出；帧预算目标：中端手机 60fps。

### 4.3 主题包系统（Theme Pack）

每个游戏 = 玩法插件 + **主题包**。主题包约定：

```
themes/night-of-ninja/
  tokens.css        # CSS variables：色板、字体、阴影、圆角
  textures/         # 桌面（榻榻米/月光渐晕）、卡背（花/影家纹）
  cards/            # 卡面 SVG/PNG
  particles.json    # 粒子预设（类型/速率/调色）
  audio/            # BGM 集 + SFX 集
```

平台壳使用统一「夜之桌游馆」主题：深靛蓝夜色 + 暖金灯笼光，标题字 Noto Serif SC，正文 Noto Sans SC。加载游戏时以 CSS variables 整体换肤，实现低成本的高辨识度氛围差异。

### 4.4 音频系统（AudioDirector）

- **解锁**：首次用户手势（点击「进入大厅」等）解锁 AudioContext，规避浏览器自动播放策略；未解锁前 UI 显示静音态提示。
- **BGM**：按场景/游戏阶段切换（大厅慵懒三味线 lofi、轮抽紧张拨弦、夜晚阶段低鼓点环境、结算短胜利曲），切换用 1.5s 交叉淡化。
- **SFX**：发牌沙沙、翻牌、手里剑 whoosh、受击闷响、按钮木质 click、聊天气泡；关键事件时 BGM 自动 duck −6dB。
- **定位感**：按座位环绕布局做简单左右 pan（受击者在你左侧则声音偏左）。
- **偏好**：总音量/BGM/SFX 三通道 + 静音，localStorage 持久化。
- **素材来源**：优先**委托或自制原创**（平台长期无版权风险）；其次 CC0 素材（freesound 等）并登记出处；不使用来源不明的「扒」素材。

## 5. 后端设计

### 5.1 房间生命周期

```
lobby ──房主开始──► playing ──终局──► result ──再来一局──► lobby
  ▲                                        │
  └──────────所有人离开/10分钟无人──────────┴──► destroyed
```

- 房间码：5 位 Crockford base32（去混淆字符），不可猜测；可选房间口令。
- 房间与对局状态**只存在服务端内存**；连接断开不影响状态推进（见 5.3）。

### 5.2 通信协议

所有消息为 JSON，双向均带单调递增 `rev`（房间状态版本号）保证顺序：

```jsonc
// C → S：玩家动作（带客户端 seq，用于幂等去重）
{ "t": "action", "rev": 106, "seq": 42,
  "action": { "type": "non:playCard", "card": "blind-assassin", "target": 5 } }

// S → C：事件（动画/音效 cue，可选按座位定向）
{ "t": "events", "rev": 107,
  "events": [ { "type": "non:assassinate", "payload": { "from": 3, "to": 5 } },
              { "type": "non:death",       "payload": { "seat": 5 } } ] }

// S → C：视图（以接收者座位过滤后的完整快照；状态小，全量推送即可）
{ "t": "sync", "rev": 107, "view": { "phase": "night", "players": [ /* ... */ ] } }
```

客户端模型：**收到事件 → 播动画 → 收到 sync → 应用状态**。重连或事件丢失时以最新 `sync` 全量对齐，动画直接跳过。

### 5.3 断线重连

- 进入房间即颁发 `sessionToken`（localStorage 保存）；断线后凭 token 重连回原座位。
- 座位保留 90 秒；期间轮到该玩家行动则挂起服务端时钟（见 5.5）。
- 房主可手动移交 AI 托管/踢人；超时不归视为放弃当回合行动。

### 5.4 隐藏信息安全

- 视图由 `clientView(state, seat)` 在服务端计算，隐藏字段**在序列化前根本不存在**（不是前端遮挡）。
- 自动化**泄露测试**：遍历所有座位序列化所有阶段的视图，扫描敏感字段名（`hand`、`house`、`rank`…）断言不出现在他人视图中。

### 5.5 时钟与超时

- 回合计时在**服务端**（不信任客户端）；超时执行该游戏的默认垫步动作（如自动出最小数字牌）。
- 计时剩余量随视图下发，客户端只做倒计时显示。

## 6. 游戏插件框架（本项目的架构核心）

每个游戏是一个实现下列接口的**纯逻辑包**（零网络、零 DOM 依赖，可直接单元测试）：

```ts
// packages/games/core
export interface GameDefinition<S extends object, A> {
  id: string;                       // "night-of-ninja"
  displayName: string;
  minPlayers: number; maxPlayers: number;
  optionsSchema?: ZodSchema;        // 房主可调选项（目标分数、计时时长…）

  setup(ctx: { seats: number[]; options: unknown; rng: Rng }): S;

  // 当前阶段元信息：谁可行动、建议时限 → 驱动服务端时钟与客户端 UI
  phaseInfo(state: S): PhaseInfo;

  // 核心：纯函数 reducer。合法则返回新状态 + 事件（供动画/音效/回放）
  applyAction(state: S, seat: number, action: A):
    | { ok: true;  state: S; events: GameEvent[] }
    | { ok: false; reason: string };

  // 按座位计算客户端视图（隐藏信息在此过滤）
  clientView(state: S, seat: number): unknown;

  // 当前座位可执行的动作描述 → 客户端据此渲染可交互元素（新游戏 UI 框架级复用）
  legalActions(state: S, seat: number): ActionUI[];
}
```

配套机制：

- **种子随机数**（mulberry32）：每局记录种子与事件日志（JSONL 落盘），对局**可复现、可回放**，也为裁判 bug 提供确定性重放条件。
- **事件定向**：`GameEvent.audience: 'all' | { seats }` —— 窥视类效果只发给窥视者本人。
- **版本锁定**：房间创建时锁定游戏插件版本号；滚动发布时进行中对局继续跑旧版逻辑，新房间用新版。

## 7. 首款游戏：忍者之夜（Night of Ninja）

> 规则概要据公开资料整理；**实现前必须对照官方规则书逐条核对**：
> https://fgbradleys.com/wp-content/uploads/Night-of-the-Ninja-Rulebook.pdf （2 人变体：https://www.brotherwisegames.com/night-of-the-ninja-2p ）

### 7.1 规则概要

- 2–11 人（最佳 5–8），玩家秘密分属**花之家**与**影之家**两个流派，各有编号 1–3 的成员与一名**领袖**；你不知道谁是队友。
- 每回合两阶段：
  1. **轮抽**：每人从 5 张忍者牌中轮抽保留 2 张（选 1 传左）。
  2. **夜晚**：所有玩家暗选一张打出，按牌上数字从小到大依次结算——数字越小越先行动且效果越强（刺杀、窥视、护卫等）。
- **回合结算**：幸存者中所出数字最小的一方流派赢得该回合并获得荣誉；率先达到目标荣誉的流派获胜（计分细节以规则书为准）。

### 7.2 映射到框架

| 规则元素 | 状态字段（服务端） | 动作 | 事件（动画/音效 cue） |
|---|---|---|---|
| 身份分发 | `players[].house/rank/leader` | —（setup） | `non:dealIdentity`（定向：只发本人） |
| 轮抽 | `draftPiles[]`、`hands[]` | `non:draftPick` | `non:cardTaken`、`non:pilePassed`（发牌飞行动画） |
| 夜晚选牌 | `playedCard` | `non:playCard{card, target?}` | `non:cardCommitted`（卡背滑入中央） |
| 依次结算 | `turnOrder/turnIdx` | —（服务端驱动） | `non:cardRevealed`、`non:assassinate`（手里剑飞行+震屏）、`non:peek`（定向）、`non:death`（卡牌灰化+家徽显现） |
| 回合结算 | `honorScores` | — | `non:houseReveal`（全桌翻牌瀑布）、`non:roundWinner`（家纹绽放粒子） |

卡牌清单（盲眼刺客、窥视、护卫等具体数量与效果）以规则书核对后固化到 `packages/games/night-of-ninja/cards.ts` 的数据表中，效果用声明式描述便于单测。

## 8. 数据与持久化

| 数据 | 存储 | 说明 |
|---|---|---|
| 用户身份（昵称/头像/偏好） | 客户端 localStorage | MVP 无账号 |
| 房间与对局状态 | 服务端内存 | 重启即失，产品上可接受（对局通常 <20 分钟） |
| 事件日志（回放） | JSONL 文件 | `data/replays/<roomId>.jsonl` |
| 战绩统计 | SQLite（M5） | 按昵称聚合胜负场次；未来可平滑升级为账号体系 |

## 9. 测试策略

1. **裁判单元测试**（最高优先级）：`applyAction` 纯函数表格驱动测试；关键场景：身份分发分布、轮抽传递、行动顺序、死亡结算、平局、终局计分。
2. **视图泄露测试**：见 §5.4，进 CI。
3. **集成测试**：内存 Socket.IO 双客户端跑房间全流程（创建→加入→开局→终局→再来一局）。
4. **E2E**：Playwright 开 N 个 browser context 模拟多玩家完整对局，截图断言关键画面。
5. **Soak**：机器人客户端批量挂房间跑随机合法动作，验证无死锁、无内存泄漏。

## 10. 部署与运维

- 宿主操作系统：**Linux**（Debian 12 / Ubuntu 24.04 LTS）。技术栈（Docker/Caddy/Node）为 Linux 原生，小规格 VPS 即可承载；开发仍在 Windows 进行，部署 = 服务器上 `git pull` + `docker compose up -d`，宿主机管理面极小。
- 单台 VPS：`docker compose up`（caddy + server，前端静态产物由 Caddy 托管），域名 + 自动 HTTPS。
- 若主要面向国内访问：域名需备案，或选用海外节点/Cloudflare Tunnel（小圈子延迟可接受）；决策点见 ROADMAP M5。
- 监控：`/healthz`、pino 结构化日志按天滚动；UptimeRobot 类外部拨测即可。
- 备份：SQLite 与 replays 目录每日快照。

## 11. 安全要点

- 一切动作服务端校验合法性（`legalActions` 为准）；动作与聊天限频。
- 聊天内容转义渲染、长度与频率限制，防 XSS 与刷屏。
- 房间码不可猜测 + 可选口令；无账号体系下的身份冒用风险由「熟人邀请制」天然缓解。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 音频/美术素材版权 | 公开后下架风险 | 自制/委托原创优先；CC0 次之并登记出处 |
| 断线导致对局卡死 | 体验致命 | 座位保留 + 服务端时钟垫步 + 房主踢人（§5.3/5.5） |
| 规则理解偏差 | 裁判错误 | 实现前对照官方规则书核对；事件日志可复现调试 |
| 动画性能（低端手机） | 掉帧 | 低配模式/设备分级缩放粒子；reduced-motion 降级 |
| 游戏玩法版权 | 已定性：自部署、免费、仅朋友圈访问 → 风险极低；完全公开化前重估 | 规则机制不受版权保护可自由重实现；美术/音频/规则文字全部自制，不复用官方素材与规则书原文；站点/房间加入口口令固定「私用」定性；公开化（无访问控制）前再评估并考虑改用自有游戏名 |
| 单人开发战线过长 | 弃坑 | 里程碑强验收标准，每个 M 结束都有「可玩可晒」产物 |
